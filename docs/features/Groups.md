## 1. Functional UI Behavior

**Entry points:**
- **`ham_groupsCmp`** — small "Alumni Groups" homepage widget listing the user's joined groups (max 10), with a search box and "Discover All" button. Clicking any group or the discover/search actions doesn't navigate itself — it dispatches a `viewgroup` event asking a parent page to route into the full module.
- **`ham_groupsDiscovery`** — the full directory page: "My Groups" / "All Groups" tabs, search, category filter dropdown, paginated group cards, and a "Start a New Alumni Group" request modal.
- **`ham_GroupsOrchestrator`** — invisible router (`isExposed: false`, not Experience-Builder placeable) that toggles between `ham_groupsDiscovery` (no `groupId`) and `ham_groupDashboard` (`groupId` set), based on a single `groupId` prop threaded in from whatever page/Aura wrapper owns the URL.

**Inside a single group (`ham_groupDashboard`):**
- User Action: Click a group card → **System Reaction:** dashboard loads group banner/header, membership button (Join/Leave/Cancel Request depending on status), notification-preference toggles, About/Offer/Guidelines text, and tabs for Discussion, Members, Resources, and (admins only) Group Admin.
- User Action: Click **Join Group** (public) → **System Reaction:** joins immediately (Active). On a **private** group → opens a "Request to Join" modal with an optional message; on submit shows a confirmation modal and the membership becomes Pending until a moderator approves it.
- User Action: Click **Leave Group** → **System Reaction:** opens a modal requiring at least one leave-reason checkbox (with free-text "Other"); confirms as a soft-delete (`Status__c = 'Left'`), preserving the reason(s).
- User Action: Post in the **Discussion** tab (`ham_groupPostComposer`) → **System Reaction:** text posts insert immediately; posts with attachments first create a hidden draft post so `lightning-file-upload` has a record to attach files to, then publish on submit. The feed (`ham_groupFeed`) refreshes via a `postcreated` event and also self-polls (15s → 5min backoff) for new posts from others.
- User Action: Type `@Name` while composing a post or comment → **System Reaction:** an inline autocomplete popover (scoped to active members of the current group) appears; selecting a suggestion inserts `@Full Name` into the text. On submit, each mentioned member who is an opted-in active member (and isn't the author themselves) gets a distinct notification — title is the group name, body is `"{Full Name} mentioned you! in {Group Name}"` (author name is masked as "Someone" if the post is anonymous).
- User Action: Pin/delete/report a post or comment, or moderate content/pending members (`ham_groupAdmin`) → **System Reaction:** admin-only actions gated by `FeatureManagement.checkPermission('Hamilton_Community_Moderator')` or an Active admin-role membership row; moderator "Take Action" sends a warn/delete/block email to the reported user.
- User Action: Admin clicks **Amplify Post** from a post's kebab menu → **System Reaction:** flags the post as amplified (badge shown to all members) and asynchronously notifies every active, opted-in group member — title is the group name, body is `"Check out this post in {Group Name}!"`.
- User Action: Member opens the bell dropdown on the group dashboard → **System Reaction:** sees three toggles — **Send Me Notifications** (master), **Tagged Notifications**, **Amplified post Notifications** — the latter two grey out when the master is off. Turning off "Amplified post Notifications" stops amplify alerts for that group only.
- User Action: Browse/bookmark/amplify a link in **Resources** (`ham_groupResources`) → **System Reaction:** admins can add resources and "amplify" one, which notifies all group members asynchronously via a platform event.
- User Action: Browse/search/filter the **Members** tab (`ham_groupMembers`) → **System Reaction:** paginated member list reusing the platform-wide Alumni connection system (send/cancel connection request, bookmark, block) rather than group-specific actions.

Navigation between all of the above is done entirely via bubbling `CustomEvent`s (`viewgroup`, `navigategroup`, `backtodiscovery`, `postcreated`, `expand`) — **no `NavigationMixin`** is used anywhere in the module. A shared `isOverride` prop threads through every component to swap in a "Kirkland" white-label theme/fallback image.

**Controller/Apex Layer:**
- **`Ham_GroupsController.cls`** → the active controller for the entire module (`without sharing`, manual authorization + `Security.stripInaccessible` for CRUD/FLS). ~37 `@AuraEnabled` methods covering: group listing/search (`getGroups`, `getPicklistValues`), group detail/membership (`getGroupDetail`, `joinGroup`, `leaveGroup`), members (`getGroupMembers`), feed/posts/comments (`getGroupFeed`, `checkForNewPosts`, `createPosts`, `createDraftPost`/`publishDraftPost`/`discardDraftPost`, `updatePost`, `togglePinPost`, `deletePost`, `createComment`, `updateComment`), bookmarks (`bookmarkPost`/`unbookmarkPost`, `bookmarkResource`/`unbookmarkResource`), resources (`getGroupResourceCards`, `addResource`, `amplifyResource`), post amplification (**`amplifyPost`** — new, mirrors `amplifyResource`), mentions (**`searchGroupMembersForMention`** — new, scoped @mention search reusing `PostAuthorWrapper`), moderation (`reportContent`, `getReportedContent`, `resolveReport`, `takeReportAction`, `getPendingMembers`, `approveMember`, `rejectMember`), tags (`searchTags`), and file attach (`attachFilesToPost`). `GroupDetailWrapper`'s notification-preference fields are now `notifyOnTagged`/`notifyOnAmplified` (previously `notifyOnLikes`/`notifyOnComments`/`notifyOnPinned`, which were UI-only and never read by any dispatch logic). `createPosts` accepts `Mentioned_Contact_Ids__c` directly on the incoming sobject (same pattern as `Tags__c`); `publishDraftPost` and `createComment` gained an explicit `mentionedContactIds` parameter since they don't take a full sobject payload from the client.
- **`GroupsController.cls`** → **DEAD CODE.** Single method (`getGroups`, `with sharing`), superseded by `Ham_GroupsController.getGroups`. Confirmed via repo-wide grep: zero LWCs import `@salesforce/apex/GroupsController.*`; its only remaining references are stale Apex-class access grants in profile metadata (e.g. `Admin.profile-meta.xml`).
- **`HAM_AlumniConnectionService.cls`** / **`HAM_AlumniDirectoryController.cls`** → reused (not Groups-specific) by `ham_groupMembers` for connection send/cancel/remove/block actions and dynamic filter metadata — the Members tab intentionally shares the platform-wide Alumni Directory connection system rather than a Groups-only one.
- **`HAM_GroupNotificationHandler.cls`** → `processNotifications()`, invoked only by the trigger below; resolves opted-in active `HAM_Group_Member__c` rows → active `User` records → hands off to `HAM_NotificationService.sendNotifications()`.

**Automation/Data Layer:**
- **Trigger:** `HAMGroupNotificationTrigger` — `after insert` on platform event `HAM_Group_Notification__e`, one-line dispatch to `HAM_GroupNotificationHandler.processNotifications(Trigger.new)`. Decouples the write path (new posts, amplified resources) from notification fan-out.
- **Async:** `System.enqueueJob(HAM_NotificationQueueable)` fires from `Ham_GroupsController.dispatchPostNotifications` (new/published posts, plus a separate enqueue for post mentions), `createComment` (comment mentions), `amplifyResource`, and **`amplifyPost`** (new); a synchronous `Messaging.CustomNotification` + `HAM_Notification__c` insert happens directly for moderator post-deletion notices; `Messaging.sendEmail` is used for moderation warn/delete/block actions. `HAM_NotificationQueueable` now has 4 constructor overloads: new-post fan-out (`List<Id> postIds>`), amplify (`Id, Id, String amplifyType`), and **mentions** (`Id sourceRecordId, List<Id> mentionedContactIds, Id authorContactId, String mentionType`) — the latter targets only the specific @mentioned members (not the whole group), excludes self-mentions, masks the author as "Someone" for anonymous posts, and is gated on `Receive_Notifications__c = true AND Notify_on_Tagged__c = true`. Both amplify paths share a `dispatchAmplifyNotifications` helper, filter recipients on `Notify_on_Amplified__c = true` (previously unconditional for resources), and send the exact copy `"Check out this {post|resource} in {Group Name}!"` with the group name as the title. All three dispatch paths share a `resolveGroupAlertTypeId()` helper for the `CustomNotificationType` lookup.
- **Objects touched:** `HAM_Group__c`, `HAM_Group_Member__c` (+ new `Notify_on_Tagged__c`/`Notify_on_Amplified__c` fields), `HAM_Group_Post__c` (+ new `Amplified_On__c`, `Mentioned_Contact_Ids__c` fields; `Is_Amplified__c` already existed and was already read by the feed UI, just never settable), `HAM_Group_Comment__c` (+ new `Mentioned_Contact_Ids__c` field), `HAM_Group_Resource__c`, `HAM_Saved_Post__c`, `HAM_Saved_Resource__c`, `HAM_Reported_Content__c`, `HAM_Group_Notification__e` (platform event), `HAM_Notification__c`, plus `Contact`/`User`/`ContentVersion`/`ContentDocumentLink`/`CustomNotificationType`/`OrgWideEmailAddress` as supporting reads. `Mentioned_Contact_Ids__c` (both objects) stores a comma-separated list of Contact Ids — same lightweight pattern as `Tags__c`, not a junction object, since it's only ever read for notification fan-out.
- **Caching:** `Cache.Session` (Platform Session Cache) holds per-contact active-group-membership lists and a per-group `lastUpdate` timestamp used by the feed's polling mechanism; explicitly invalidated on join/leave/approve/block.
- **Unrelated namesake:** `HAM_AttendeeGroupMigrationBatch.cls` is a one-time ETL batch migrating legacy Cvent "Attendee Group" event-billing records into `HAM_Event_Attendee_Group__c` — a different "Groups" concept (event attendee billing) with no relation to the alumni/member Groups UI above.

## 3. Current Technical Logic Summary
A user reaches Groups either through the `ham_groupsCmp` homepage widget or the `ham_groupsDiscovery` directory page, both of which query `Ham_GroupsController.getGroups` and communicate the chosen group purely via bubbling `viewgroup`/`navigategroup` events (no NavigationMixin) up to `ham_GroupsOrchestrator`, which flips its single `groupId` state to render `ham_groupDashboard` instead of Discovery. The dashboard wires `getGroupDetail` and composes the Discussion (`ham_groupFeed`/`ham_groupPostComposer`), Members (`ham_groupMembers`), Resources (`ham_groupResources`), and Admin (`ham_groupAdmin`) tabs, all of which call further `Ham_GroupsController` `@AuraEnabled` methods imperatively or via `@wire`. Writes (posts, comments, joins, moderation actions) run through manual membership/role checks and `Security.stripInaccessible` since the controller is `without sharing`, then insert/update/delete the relevant `HAM_Group_*` custom objects. Certain writes (new posts, amplified resources) also publish `HAM_Group_Notification__e` platform events, picked up by `HAMGroupNotificationTrigger` → `HAM_GroupNotificationHandler`, which resolves opted-in members to active Users and dispatches push notifications asynchronously — decoupling the UI's write path from notification fan-out.
